# worktree sync

현재 저장소에 등록된 워크트리를 한 번에 갱신합니다. 각 브랜치의 upstream을
FF-only로 따라잡은 다음, 명시된 부모 브랜치의 변경을 의존 순서대로 반영합니다.
master/develop 이름은 예약되어 있지 않으며 설정한 브랜치에 동일하게 적용됩니다.

## 범위와 실행 순서

`gz-git worktree sync`는 현재 저장소와 연결된 모든 워크트리를 대상으로 합니다.
저장소 안의 하위 디렉터리나 연결된 워크트리에서 호출해도 같은 대상을 찾습니다.
저장소 밖의 디렉터리를 인자로 주면 기존 저장소 스캐너로 하위 저장소를 찾고,
공통 Git 디렉터리가 같은 워크트리는 한 번만 처리합니다. 저장소와 워크트리는
순차 처리하며, 병렬 실행 옵션은 첫 버전에서 제공하지 않습니다.

1. 설정, 필터, 부모 그래프, 작업 상태를 검사합니다.
1. 필요한 upstream을 저장소·원격별로 한 번 fetch합니다.
1. 부모부터 각 브랜치의 upstream 갱신과 부모 변경 반영을 수행합니다.
1. 결과와 차단 이유를 출력합니다. 차단된 대상이 있으면 종료 코드는 0이 아닙니다.

fetch는 필요한 원격 브랜치를 원격 추적 ref에만 반영하며 태그나 로컬 브랜치를
갱신하지 않습니다. 같은 원격을 사용하는 워크트리의 유효 Git 설정과 URL 해석이
다르면 해당 원격의 갱신을 차단합니다. 원격별 한 번의 fetch를 보장하기 위한
보수적인 제한이며, 설정 값이나 자격증명은 진단에 출력하지 않습니다.
실행 직전 HEAD, 체크아웃 브랜치, 변경 원천의 SHA와 작업 상태를 재확인합니다.
다른 프로세스의 Git 작업을 독점 잠금하는 기능은 아니므로 실행 중에는 같은
워크트리에서 별도 Git 작업을 시작하지 않는 것이 좋습니다.

## 설정

대표 워크트리의 `.gz-git.yaml`에 부모 관계를 선언합니다. 연결된 워크트리의
설정 파일이 다르더라도 대표 워크트리를 기준으로 유효 설정을 읽습니다.
bare 저장소에서 생성한 워크트리들은 bare 저장소 디렉터리를 설정 기준으로 씁니다.

```yaml
branch:
  worktreeSync:
    upstream: ff-only
    rules:
      - match: develop
        parent: master
        strategy: ff-only
      - match: feature/*
        parent: develop
        strategy: rebase
```

이 설정은 master를 upstream까지 갱신하고, develop을 upstream 및 master까지
FF한 뒤 feature 브랜치에 develop 변경을 반영합니다. develop과 master가
분기되어 있으면 develop과 그 하위 작업은 차단됩니다.

| 설정       | 의미                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| `upstream` | 생략하거나 `ff-only`. 원격의 같은 브랜치에 대한 자동 rebase는 지원하지 않음 |
| `match`    | 브랜치 이름 또는 Go `path.Match` 패턴                                       |
| `parent`   | 부모 로컬 브랜치의 정확한 이름. 해당 브랜치의 워크트리가 필요               |
| `strategy` | `ff-only` 또는 `rebase`. 필수 지정                                          |

FF로 반영할 수 있으면 `rebase` 규칙에서도 FF합니다. 부모 변경이 이미 포함되어
있으면 브랜치를 이동하지 않습니다. 로컬 브랜치가 upstream보다 앞서 있기만 하면
그 커밋을 유지하며, 서로 분기된 경우 FF-only로 차단합니다.

브랜치명과 정확히 일치하는 규칙이 패턴보다 우선합니다. 같은 이름의 중복 규칙,
여러 패턴에 의한 모호한 매칭, 자기 참조와 순환 관계는 거부합니다.
`*`는 `/`를 넘지 않으므로 `feature/*`는 `feature/api`를 선택하지만
`feature/api/v2`는 선택하지 않습니다.

global → profile → project 순서로 우선순위가 높아집니다. `worktreeSync`는
전체 객체를 교체하며 규칙 목록을 합치지 않습니다. 프로젝트에서
`worktreeSync: {}`를 지정하면 상위의 부모 규칙을 비우고 upstream FF-only만
사용합니다. 기존 `defaultBranch`와 `integrationBranch`는 부모 계층이 아닙니다.

## 옵션과 결과

| 옵션                       | 동작                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------ |
| `--dry-run`, `-n`          | fetch 없이 기존 원격 추적 ref로 계획만 출력. 로컬 브랜치와 작업 파일을 변경하지 않음 |
| `--format json`, `-f json` | 저장소별 계획·결과를 JSON 배열로 출력                                                |
| `--include`                | 선택할 브랜치 패턴. 필요한 부모는 결과에 표시하고 함께 포함                          |
| `--exclude`                | 제외할 브랜치 패턴. 필요한 부모가 제외되면 자식 차단                                 |
| `--scan-depth`, `-d`       | 저장소 밖의 디렉터리를 검색할 깊이. 기본 1                                           |

JSON에는 저장소와 워크트리 경로, 브랜치, 부모, 자동 포함 여부(`implicit`),
각 단계의 원천 ref·정책·작업·SHA·상태가 들어갑니다. 워크트리는 실행 전
`planned`, 실행 후 `done`, 실패하거나 실행할 수 없으면 `blocked`입니다.
단계별 상태는 `planned`, `done`, `failed`이며 `action`은 `up-to-date`, `ff`,
`rebase`입니다. 실패 전 완료된 단계도 그대로 기록합니다.

미리보기의 원격 추적 ref는 오래된 값일 수 있습니다. 실제 실행은 fetch 후
계획을 다시 만들므로 미리보기와 결과가 달라질 수 있습니다.

## 차단과 복구

다음 대상은 자동으로 변경하지 않습니다.

- 미커밋 변경, detached HEAD, 잠김·정리 대상 워크트리
- 진행 중인 merge/rebase/cherry-pick/revert/bisect 및 index 잠금
- upstream과 부모 규칙이 모두 없는 브랜치
- upstream이 로컬 브랜치인 대상. 로컬 upstream을 해제하고 명시적 부모 규칙으로 지정해야 함
- upstream이 사라졌거나 fetch가 실패한 브랜치
- 부모 워크트리가 없거나 제외되었거나 차단된 브랜치
- 계획 이후 HEAD, 체크아웃 브랜치, 원천 ref가 바뀐 대상
- 부모 자체의 rebase가 필요한 다단계 관계와 로컬 merge 커밋의 rebase

첫 버전의 rebase는 말단 브랜치만 지원합니다. 제외된 자식이 있더라도 부모의
rebase는 차단합니다. 이전 부모 위치를 추적하는 다단계 rebase는 지원하지 않습니다.

rebase 충돌은 해당 워크트리에 남겨두고 경로와 Git 오류를 출력합니다. 그 경로에서
충돌을 해결한 뒤 Git의 rebase continue 또는 abort 절차를 수행해야 합니다.
해결 후 다시 sync할 수 있습니다. 독립 작업의 성공은 유지하며, 전체 롤백은 하지
않습니다. 자동 stash, push, 강제 push는 수행하지 않습니다. 이미 원격에 게시한
feature를 rebase하면 원격과 분기될 수 있으므로 이후 게시 방법은 별도로 결정해야 합니다.
